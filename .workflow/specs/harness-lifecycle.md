# Resume Builder 轻量 Harness 生命周期规范

## 1. 规则定位

本文档定义 `resume-builder` 的需求、实现、验证、审查和知识沉淀闭环。流程不绑定任何 MCP、Skill、CLI、浏览器或其他具体工具，可选能力通过 `.workflow/lifecycle-plugins.json` 按 Hook 注入。

任何新增、修改、修复或优化请求先完成复杂度路由，不得把“需要改代码”直接等同于“必须创建 PRD”。

### 1.1 直接修改车道

同时满足以下条件时直接修改：

1. 目标、范围和可观察验收已经清晰，不需要继续做产品决策。
2. 影响局部、风险低、容易回退，不改变公共接口或关键业务不变量。
3. 不涉及数据库结构或迁移、权限安全、支付、跨服务协议、复杂状态流或不可逆外部副作用。

典型场景包括文案与提示调整、样式和间距细节、局部交互优化、明确根因的小修复、配置或文档校正。直接修改车道只需记录简洁目标、范围和验收，读取相关 Spec 后实现，并执行与改动风险匹配的针对性验证；不创建 PRD，不要求逐阶段输出，不默认生成独立归档或 Spec 条目。

### 1.2 完整 Harness 车道

满足任一条件时进入完整 Harness：

1. 新增产品能力、用户流程、页面主体或重要交互。
2. 涉及跨模块、跨前后端、公共接口契约、持久化模型或数据库迁移。
3. 涉及权限、安全、支付、隐私、并发一致性、复杂状态机或高风险外部操作。
4. 需求存在会改变方案或验收的关键歧义，或实施范围预计持续扩展。
5. 用户明确要求 Brainstorm、PRD、设计、完整 Harness 或正式归档。

完整车道依次执行 Brainstorm、PRD、可选 UI、Implement 与 Break Loop、Quality Gate、Submit / Review 和 Archive。

### 1.3 询问车道

无法可靠判断复杂度，或直接修改与完整 Harness 都合理时，只询问一次“本次是否创建 PRD”。当前客户端支持选项弹窗时优先使用弹窗，至少提供“直接修改”和“创建 PRD”两个选择；不支持时使用一句简短问题。用户选择不创建或明确要求一次性修改后，进入直接修改车道，不得换一种说法重复追问。

直接修改过程中如果出现公共契约、数据结构、权限或明显跨层范围，应暂停扩展并询问是否升级为 PRD。跳过 PRD 不会绕过破坏性操作、外部副作用、Git / PR 和其他明确授权门禁。

纯解释、只读排查和信息查询不进入变更车道，也不创建 PRD。

## 2. 核心原则

### 2.1 结果是门禁，工具不是门禁

1. MCP、Skill、CLI、浏览器、官方文档和人工检查都是可选手段，不得把某个工具名称作为阶段通过条件。
2. 只在工具能明显降低错误率、补足时效性事实、提高设计质量或提供必要验证证据时使用。
3. 同一目标已有本地代码、类型定义、锁文件、日志或可靠文档可低成本证明时，不得为调用工具而调用工具。
4. 工具不可用时使用合理替代方案；无法替代的验证必须标记为 `未执行` 并说明影响，不得伪造结论。
5. 涉及最新外部事实时仍需取得可靠来源，但不限定来源通道。

### 2.2 单一事实源

1. 完整 Harness 的范围、决策、任务和验收以 PRD 为准；直接修改车道以用户指令和简洁任务记录为准。
2. 长期规范以 `AGENTS.md` 和 `.workflow/specs/` 为准。
3. 代码、配置和数据库现状必须以当前工作区的实际证据为准。
4. 不在对话、计划、PRD、归档中重复粘贴同一份长清单；使用路径和状态引用。

### 2.3 渐进读取与低 Token

1. 先读入口和任务相关规则，再读最小必要目录与代码。
2. `.workflow/specs/` 只读取与任务关键词、模块和风险相关的文件，不得默认全量载入。
3. 需求已清晰时不重复询问已确定事项，直接记录决策或显式假设。
4. 问题集中成一轮，只询问会改变范围、方案或验收的关键决策。
5. 状态更新以阶段边界、范围变化、阻塞和验证结果为主，不为每个微步骤重复复述背景。
6. 实现状态按可交付切片更新，不要求每修改一行就回写文档。

### 2.4 插件注入

1. 进入有插件需求的 Hook 前，先根据任务语义和当前修改面生成少量标准标签。
2. 使用 `.workflow/scripts/resolve-lifecycle-plugins.ps1` 解析当前 Hook；只调用返回的 `selected` 插件。
3. Skill 读取解析结果中的 `entry`，MCP 使用解析结果中的 `provider`；不得把完整插件目录或所有 Skill 内容放入上下文。
4. `manual` 插件必须通过 `RequestedPlugins` 显式选择，`requiresAuthorization` 插件还必须传入已获得的用户授权。
5. 插件不可用时按 `fallback` 降级或标记未执行，不得因为工具缺失跳过阶段结果。
6. 完整选择、标签、授权和扩展协议以 `.workflow/specs/lifecycle-plugins.md` 为准。

## 3. 固定目录

| 内容 | 固定位置 | 规则 |
| --- | --- | --- |
| 长期 Spec | `.workflow/specs/` | Brainstorm 中途按相关性读取；只写稳定、可复用知识 |
| 插件注册表 | `.workflow/lifecycle-plugins.json` | 声明 MCP、Skill、Hook、触发条件、优先级和降级 |
| 任务 PRD | `docs/requirements/YYYY-MM-DD-<topic>.md` | 仅完整 Harness 在实现前建立，作为任务期单一事实源 |
| 可选 UI 设计 | `docs/designs/` | 只有任务确有 UI 设计产物时创建 |
| 完成归档 | `.workflow/archive/YYYY-MM-DD-<topic>/` | 完整 Harness 或用户明确要求时生成 `summary.md` |

`docs/requirements/` 中的权威 PRD 和 `docs/designs/` 中的权威设计文档可以保留原位，归档通过路径引用，避免复制全文。临时分析、质量记录和 Review 记录如需长期保留，应移动或汇总到对应归档目录。

## 4. 完整 Harness 七阶段生命周期

本节只适用于完整 Harness。直接修改车道在读取相关 Spec 后直接进入实现和针对性验证，不需要为跳过的阶段生成占位文档。

### 4.1 Brainstorm：需求梳理问答

目标是把模糊请求转成可决策的问题定义，而不是立即扩写长方案。

执行顺序：

1. 用最小上下文确认现状、目标、受影响角色和可能修改面。
2. 汇总会改变实现或验收的关键问题；用户已明确的内容不得重复询问。
3. 在形成最终决策前，列出 `.workflow/specs/` 文件并读取 `conventions.md` 以及与任务直接相关的 Spec；没有相关 Spec 时记录“未发现相关规范”。
4. 对照 Spec 处理范围、术语、分层和历史经验冲突；发现冲突时明确指出并按仓库优先级解决。
5. 输出简洁决策快照：目标、范围、非目标、关键流程、约束、假设、未决项。
6. 需要远程上下文、外部调研或领域增强时，分别解析 `brainstorm.context`、`brainstorm.research` 或 `brainstorm.enrich`。

可直接结束本阶段的条件：关键决策已经明确，剩余假设可逆且风险低。无法合理推断的高风险决策必须等待用户回答。

### 4.2 PRD：需求与验收固化

只有路由为完整 Harness 的任务才在实现前生成 PRD。PRD 至少包含：

1. 背景与问题。
2. 目标、范围和非目标。
3. Brainstorm 决策与必要假设。
4. 用户流程或业务流程。
5. 跨层输入、输出、状态、错误和权限契约。
6. 可按顺序执行的任务清单。
7. 可检查的验收标准。
8. 验证计划、风险和未决项。
9. 执行状态与最终验收结果。

验收标准必须描述可观察结果，不能只写“功能正常”“代码完成”。直接修改车道只记录等价的简洁目标、范围和验收，不额外创建 PRD。

需要领域能力补充 PRD 时解析 `prd.enrich`；没有匹配插件时直接基于 Brainstorm 结果生成，不得强行调用工具。

### 4.3 UI：基于 PRD 的初步设计，可选

只有新增可视界面、大幅调整布局或交互、用户明确要求设计时进入本阶段。纯后端、数据、规则和不改变视觉的修复直接标记为 `不适用`。

直接修改车道中的样式、间距、文案或局部交互细节不进入独立 UI 阶段，按现有设计系统修改并完成针对性视觉验证即可。

初步设计至少说明：

1. 信息架构与关键操作路径。
2. 默认、加载、空、错误、禁用和成功状态。
3. 响应式、可访问性和现有设计系统复用方式。
4. 设计与 PRD 验收项的映射。

可以按需使用设计类 Skill、MCP、浏览器、图片工具或现有组件库，也可以直接基于仓库设计系统完成。选择依据是任务收益，不是工具优先级。

进入设计时解析 `ui.design`；用户显式选择的设计插件优先于自动匹配结果。

### 4.4 Implement：按任务依据实现与 Break Loop

实现要求：

1. 完整 Harness 按 PRD 的最小可交付切片推进；直接修改按简洁目标和验收推进，优先修正契约和根因，再处理表现层。
2. 每处修改都应能追溯到 PRD、直接修改记录、仓库规则或本次改动造成的必要收尾。
3. 禁止顺手重构、无关格式化、扩展未要求功能或修改无关脏工作区内容。
4. 完整 Harness 的范围、契约或验收变化时先更新 PRD；直接修改出现明显扩展时先重新路由，不得静默扩大范围。
5. 只有确实需要领域或组件支持时解析 `implement.support`。

#### Break Loop

在实际 Bug 修复完成后、同类 Bug 复发时，或一次修复失败后继续尝试前，必须做一次简洁的 Break Loop。普通功能开发不得为了流程完整生成空复盘。

Break Loop 必须回答：

1. **根因类别**：规格缺口、错误假设、状态或生命周期、跨层契约、数据一致性、并发时序、缓存、权限、安全、异常处理、环境配置或工具链中的哪一类。
2. **失败原因**：历史修复或本轮失败尝试为什么只处理症状、遗漏数据链路、缺少证据或被上下文漂移影响；没有历史失败时明确写 `不适用`。
3. **正确修复**：本次修改如何作用于根因，而不是仅遮盖表现。
4. **预防机制**：应增加哪项不变量、边界检查、复用点、验证清单、日志或规范约束。
5. **验证证据**：什么证据证明根因已被处理，哪些风险仍未验证。
6. **知识捕获**：只把可跨任务复用的结论写入相关 Spec 或 `.workflow/specs/learnings.md`，不得写入一次性堆栈、临时路径或冗长流水账。

存在已注册的根因分析增强插件时可解析 `break_loop.analyze`；没有插件不影响 Break Loop 本身执行。

### 4.5 Quality Gate：生成后全面校验

在代码完成后、提交前以及长会话出现多轮修改或范围变化时执行。完整 Harness 覆盖全部适用维度；直接修改只执行与改动风险相关的检查，不为无关维度生成冗长的占位结果。长会话检查先重读 PRD 或直接修改记录、相关 Spec 和当前 diff，确认没有上下文漂移。

质量门禁覆盖：

1. **规格符合性**：逐条映射适用的 PRD 或直接修改记录、验收标准、仓库规则和非目标。
2. **改动质量**：检查 diff 范围、语法、格式、静态检查、错误处理、安全和无关改动。
3. **类型与构建**：执行任务相关且仓库已有的类型检查、编译或构建命令。
4. **测试与行为验证**：执行 `.workflow/specs/testing.md` 允许的现有测试或验证方式；禁止新增或修改测试代码、脚本、fixture 和 mock。
5. **跨层数据流**：从入口、状态 / Service、API、业务层、持久化到响应 / UI 回显追踪字段、权限、错误和状态变化。
6. **代码复用**：检查是否重复已有常量、组件、服务、校验、Mapper、DTO 或错误处理能力。
7. **一致性**：检查命名、契约、双后端行为、配置、文档和同类交互是否漂移。
8. **运行证据**：按风险选择浏览器、接口、日志、数据库或人工验证，不绑定具体工具。

需要运行时或浏览器证据时解析 `quality_gate.verify`；静态证据已足够的文档任务无需调用插件。

每项结论使用 `通过`、`不通过`、`未执行`。`不通过` 必须修复后重跑受影响项；`未执行` 必须写明原因和残余风险，不能伪装成通过。必要验收未通过时不得声称任务完整完成。

### 4.6 Submit：提交 / PR 与可选 Code Review

完整 Harness 的 Quality Gate 完成后，合并询问用户提交授权和 Review 选择，避免反复确认。直接修改车道只有在用户要求提交、推送、PR 或 Review 时才进入本阶段，否则直接报告这些操作未执行。建议选项：

1. 不执行 Review，按授权提交 / 推送 / 创建 PR。
2. 只执行 Review，先反馈问题再决定是否修复和提交。
3. 执行 Review，并预先授权修复指定严重级别的问题后复验。

约束如下：

1. 未获得明确授权，不得执行 commit、push、创建或合并 PR。
2. Review 可以使用仓库 Skill、其他工具或直接代码审查，不绑定实现方式；结果必须包含严重级别、证据、文件位置和影响。
3. 用户已预授权修复范围时可直接修复；未预授权时，Review 后只需询问一次是否修复。
4. 修复审查问题后必须重跑受影响的 Quality Gate；必要时复审，直到问题关闭或用户明确接受残余风险。
5. Git 分支、提交信息、提交说明和远程操作继续遵守 `.workflow/specs/git.md`。
6. Review、Review 修复和远程协作分别使用 `submit.review`、`submit.review_fix`、`submit.remote`；后两者涉及副作用时必须传递已有用户授权。

### 4.7 Archive：归档与 Spec 回写

完整 Harness 验收完成或用户明确要求归档时，在 `.workflow/archive/YYYY-MM-DD-<topic>/summary.md` 记录：

1. PRD、可选设计和相关产物路径；没有 PRD 时明确记录直接修改车道。
2. 最终实现范围与未完成项。
3. Quality Gate 的通过、未执行和残余风险。
4. Break Loop 结论或 `不适用`。
5. Review、commit、push 和 PR 的实际状态。
6. 写回 Spec 的条目与位置。

只有用户明确要求记录个人长期偏好时，才解析 `archive.preference`，并传递用户授权；项目事实始终写回仓库 Spec。

归档必须简洁，只保留可追溯事实。长期经验写入最相关的 Spec；找不到归属时写入 `.workflow/specs/learnings.md`。经验必须包含适用条件、机制和预防方式，不得把任务日志直接复制进 Spec。直接修改车道默认不归档、不回写 Spec，只有产生稳定且跨任务可复用的新知识时才更新对应 Spec。

## 5. 阶段闭环与停止条件

1. 完整 Harness 的阶段输出存在且满足下一阶段输入时自动前进，不需要为常规阶段切换反复请求确认；直接修改车道不生成阶段占位输出。
2. 只有高风险歧义、破坏性操作、外部副作用、提交 / 推送 / PR 或用户要求确认时才等待授权。
3. 发现范围冲突、无关文件被意外修改、必要验证持续失败或事实证据不足时停止当前阶段，先处理阻塞。
4. 交付说明只汇总最终改动、验证结果、未验证项、归档位置和 Git / PR 状态，不重复整份 PRD。

## 6. 完成定义

任务完成至少满足：

1. PRD 或轻量等价记录与实际改动一致。
2. 必要验收已通过，未执行项和残余风险已披露。
3. Quality Gate 已完成且不存在未处理的阻断问题。
4. Bug 修复已按触发条件完成 Break Loop。
5. 完整 Harness 中用户已决定是否 Review；直接修改只在用户要求时询问 Review。任何 Git 和 PR 操作都有明确授权。
6. 完整 Harness 已归档；直接修改仅在用户要求或产生需要保留的任务产物时归档。可复用经验按适用条件写入 Spec。

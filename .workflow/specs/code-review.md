# Code Review 与修复流程规范

## 1. 适用范围

适用于准备提交、处理 PR Review、修复审查问题或用户明确要求代码审查的场景。执行时机位于 Harness Quality Gate 之后、`git commit` 之前。

## 2. Review 选择

准备提交时，应将提交授权与 Review 选择合并询问，避免多轮形式化确认。用户可以选择：

1. 跳过 Review，按授权继续提交或 PR 流程。
2. 仅执行 Review，先反馈结果再决定是否修复。
3. 执行 Review，并预先授权修复指定严重级别或明确范围的问题。

未经用户选择，不得默认执行或跳过 Review；未经明确授权，不得执行 commit、push、创建或合并 PR。

## 3. 执行方式

1. Review 可以使用仓库 `code-review` Skill、其他可用工具或直接代码审查，不得把某个 Skill 作为强制门禁。
2. 选择方式应考虑变更规模、风险、工具可用性和 Token 成本，不得为了调用工具重复读取同一上下文。
3. 审查结果必须以问题为主，包含严重级别、文件位置、证据、影响和建议；无问题时明确说明残余风险与未验证项。
4. 使用仓库 Skill 时继续遵守该 Skill 的报告格式，但 Skill 规则不得覆盖用户授权、测试代码禁令和仓库范围边界。

## 4. Review 结果修复

1. 用户已在 Review 前授权修复范围时，可以直接修复范围内问题，不再重复询问。
2. 用户只选择 Review 或未授权修复时，反馈结果后询问一次是否修复，不得自动修改。
3. 修复可以使用 `code-review-fix` Skill、其他工具或直接实现，不绑定具体方式。
4. 修复必须限定在审查问题及其必要收尾，禁止夹带无关重构。
5. 修复后必须重跑受影响的 Quality Gate；必要时复审，直到问题关闭或用户明确接受残余风险。
6. 用户拒绝修复时不得继续自动修改，并应记录未修复问题对提交或合并的影响。

## 5. 提交边界

1. Review 结论不等于提交授权。
2. 跳过 Review 不等于跳过 Quality Gate。
3. 存在未处理的阻断问题时不得声称适合合并；是否仍提交由用户在获知风险后决定。
4. 分支、提交信息、提交说明、推送和 PR 操作遵守 `.workflow/specs/git.md`。

# Resume Builder 前端强制规则

## 1. 规则定位

本文档用于定义 `resume-builder` 仓库前端范围内的产品背景、目标边界、目录协作方式、页面设计要求、代码分层要求与交付限制。

本仓库前端不是普通的简历模板展示站，而是一个服务求职场景的交互前台，承担 **简历编辑、简历优化、AI 面试** 的核心用户体验，目标是帮助求职者更快、更精准地完成简历准备与面试通关。

凡涉及前端页面、新增组件、模板扩展、交互调整、状态管理、接口调用定义、服务编排和样式设计的改动，默认都必须遵守本文档。

注意：
- 本文档属于仓库级强制规则，不视为普通说明文档。
- 本文档适用于前端相关目录与文件，包括但不限于 `src/` 下的页面、组件、模板、接口定义、服务与状态管理代码。
- 如当前实现与本文档冲突，后续改动应优先向本文档靠拢；如确需例外，应先更新规则文档，再改代码。

---

## 2. 产品背景与前端目标

前端必须始终围绕以下业务目标展开：

1. 简历编辑
   - 为用户提供结构化、可视化、可导出的简历编辑体验。
   - 保证模板、版式、字段组织和预览行为稳定一致。

2. 简历优化
   - 提供 AI 优化交互入口，帮助用户对简历内容进行润色、重写、提炼与表达优化。
   - 输出体验必须服务真实求职与面试场景，禁止页面表达偏离业务主线。

3. AI 面试
   - 提供 AI 面试入口、过程交互、会话展示与反馈承接界面。
   - 界面重点应是信息清晰、节奏稳定、反馈可理解。

4. 一体化体验
   - 简历编辑、简历优化、AI 面试必须在交互语言、视觉风格和信息架构上保持统一产品感。
   - 禁止生成与当前产品无关、无业务承接、仅为展示效果存在的页面。

## 3. 前端执行原则

### 3.1 规则读取要求

1. 处理前端任务时，必须先阅读并遵守 Spec 目录下与前端相关的规范。
2. Spec 目录与入口规范共同构成仓库级强制约束；如无更高优先级用户指令，不得绕过。
3. 前端改动除遵守本文档外，还必须同步遵守全局、代码规范与测试验证规则。
4. 前端改动涉及页面交互验证或多步骤需求时，必须同步遵守轻量 Harness 生命周期规则。

### 3.2 目标导向原则

1. 所有页面、组件、交互和模板都应围绕求职、简历、面试主线展开。
2. 禁止脱离现有业务语义，随意生成无关模块、无关页面或演示性代码。
3. 新增功能必须与现有目录职责、主题风格、业务流程保持一致。

### 3.3 文件作者标识约束

1. 新增或修改的前端文件必须标记作者信息，例如注释头或元数据。
2. 作者必须为 `jf`。
3. 禁止出现作者为 `ai` 的标识，包括但不限于 `author: ai`、`作者：ai`、`created by ai`。

## 4. 前端目录与分层约束

当前前端目录必须围绕现有结构演进，包括但不限于：

```text
src/
├─ api/
├─ assets/
├─ components/
├─ config/
├─ constants/
├─ services/
├─ stores/
└─ templates/
```

强制要求：
- 编写前端代码时，必须严格遵守现有目录分级规则，优先复用现有目录与子目录语义。
- 禁止绕开当前结构，随意在外层新增新的平级目录。
- 禁止在非该功能目录下新增不属于该功能的文件。
- 如确需扩展目录，优先在现有目录内按功能继续细分；无法归类时，必须先更新规则文档。

---

## 5. 页面设计与视觉一致性约束

当 AI 设计新页面、新模块界面或大幅调整页面样式时，必须遵守以下要求：

1. UI 初步设计只在完整 Harness 的 PRD 涉及新增可视界面、大幅布局或交互调整时进入；样式、间距、文案和局部交互细节可走直接修改车道。
2. 可以按需使用 `UI-Ux-Pro-Max`、`Frontend Design`、设计类 MCP、浏览器、图片工具或现有组件库，不得把任一工具设为强制前置条件。
3. 工具选择应以能否补足当前任务所需的设计事实和验证证据为准；工具不可用时可基于现有设计系统继续，不得因此伪造设计或验证结论。
4. 设计结果必须遵守当前页面已经建立的主题风格、颜色配比和样式规范。
5. 禁止随意生成与当前产品不同风格的新页面。
6. 禁止为了“更酷”或“更有设计感”而破坏现有模板体系、品牌感和交互一致性。

---

## 6. 前端代码组织约束

1. AI 每次生成的单个前端代码文件内容不得超过 `1000` 行。
2. 超过 `1000` 行时，必须按功能、类型或职责进行拆分，禁止继续堆叠在单文件中。
3. 组件、页面、状态、服务、接口定义应尽量保持单一职责。
4. 禁止把页面结构、业务逻辑、接口定义、数据转换全部塞进同一个文件。

---

## 7. 前端 API 与 Service 边界

1. 前端 `api/` 层只负责接口请求定义，不承载业务逻辑。
2. 与接口调用相关的业务编排、数据加工、组合调用、状态联动逻辑，必须放在 `services/` 或对应职责层中。
3. 禁止在 `api/` 文件中编写复杂判断、流程控制、状态处理、兜底策略。

---

## 8. 简历模板 PDF 导出规范

1. 简历模板在浏览器预览和 PDF 导出中的渲染环境不同，涉及 `html2canvas` 导出副本时，必须优先修正导出态样式，不得直接改正常预览模板样式。
2. 基本信息图标在 PDF 中出现垂直偏移时，正确做法是只调整导出副本中的外层图标盒 `.pdf-export-meta-icon-box`。
3. 当前已验证的对齐值为 `top: 7px`，仅适用于 `.paper.pdf-exporting` 导出态，不得扩散到普通预览态。
4. 导出态图标必须保持原始 SVG 组件体系，不得为了 PDF 对齐替换为文字、表情或伪图标。
5. 修改此类问题后，必须重新导出 PDF 并人工核对 WPS / 浏览器 PDF 预览中的基本信息图标与文字基线。
6. 预览分页线必须与纸张处于同一个缩放舞台，使用未缩放 A4 坐标计算，不得在缩放后的叠加层里二次换算。
7. 当前已验证的预览分页线校准值为 `PDF_PAGE_BREAK_PREVIEW_OFFSET = 16`，用于让预览分页线对齐实际 PDF 导出分页位置。
8. `PDF_PAGE_BREAK_PREVIEW_OFFSET = 16` 仅适用于浏览器预览分页线坐标，不得扩散到 A4 高度、PDF 切片高度、模板样式或导出态样式。

正确示例：

```css
:global(.paper.pdf-exporting .pdf-export-meta-icon-box) {
  position: relative;
  top: 7px;
}

:global(.paper.pdf-exporting .pdf-export-meta-icon-box .meta-icon-svg) {
  margin-top: 0;
  transform: none;
}
```

```ts
const A4_HEIGHT = Math.round(A4_WIDTH * A4_RATIO)
// 预览分页线按用户实测的导出分页位置向上校准。
const PDF_PAGE_BREAK_PREVIEW_OFFSET = 16

breaks.push(i * A4_HEIGHT - PDF_PAGE_BREAK_PREVIEW_OFFSET)
```

错误示例：

```css
/* 错误：直接移动 SVG 本体容易导致 SVG 视口裁切，出现图标只显示一半。 */
:global(.paper.pdf-exporting .pdf-export-meta-icon-box .meta-icon-svg) {
  transform: translateY(4px);
}
```

```ts
// 错误：为了解决垂直偏移而重写 viewBox / getBBox 会引入不同图标尺寸、留白和视觉比例的新问题。
normalizePdfMetaIconViewBox(icon)
```

```ts
// 错误：把 SVG 转成 data:image/svg+xml 的 img 会改变渲染链路，并增加图片加载等待与颜色继承风险。
iconBox.replaceChildren(createPdfMetaIconImage(icon))
```

```ts
// 错误：修改 A4 高度会破坏预览纸张、分页线和 PDF 坐标体系的一致性。
const A4_HEIGHT = Math.round(A4_WIDTH * A4_RATIO) - 16
```

```ts
// 错误：修改 PDF 切片高度会改变实际导出分页，不是预览线校准。
const pagePixelHeight = Math.round(canvas.width * A4_RATIO) - 16
```

```css
/* 错误：用 CSS transform 视觉硬挪分页线，会在缩放场景重新引入坐标偏差。 */
.page-line {
  transform: translateY(-16px);
}
```

## 9. 前端验证与交付要求

1. AI 每次完成前端代码编写后，必须严格执行 `npm run lint`。
2. `lint` 必须通过，才可认为该次前端改动完成。
3. 如改动影响类型或构建稳定性，可继续使用测试验证规则允许的现有命令进行补充验证。
4. 涉及页面结构、样式、交互、按钮状态、弹窗、表单或流式渲染时，必须完成浏览器级或等价人工交互验证，但不绑定具体浏览器工具；环境不具备条件时必须说明未验证项和风险。
5. 所有验证不得新增测试代码，测试代码禁令与允许验证方式统一遵守测试与验证强制规则。

---

## 10. 测试代码约束

前端任务的测试代码禁令、允许验证方式和交付验证说明统一遵守测试与验证强制规则。

## 11. 结论

前端的一切改动，都必须服务“帮助求职者更快、更精准地进行面试并提升通关效率”这一核心目标。

因此必须同时保证：

- 产品方向不跑偏。
- 页面风格不失控。
- 目录分层不混乱。
- 模板体系不被破坏。
- 接口定义与业务逻辑边界清晰。
- AI 产出的前端代码可持续维护。
